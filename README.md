# سامانه هوشمند مانیتورینگ رسانه شرکت ملی پخش فرآورده‌های نفتی ایران

سامانه پایش و تحلیل اخبار مرتبط با صنعت نفت، توزیع فرآورده‌های نفتی و مناطق عملیاتی؛ شامل گردآوری RSS/HTML، ثبت داده در PostgreSQL، حذف موارد تکراری، تحلیل خبر، خوشه‌بندی رویداد و رصد موارد نیازمند راستی‌آزمایی.

> **وضعیت فعلی پیاده‌سازی:** پایگاه داده PostgreSQL در schema مستقل `niopdc_app` آماده‌سازی شده است. داده مرجع فعلی شامل ۳۷ منطقه عملیاتی و ۱۸ تعریف منبع رسانه‌ای است. این اعداد به معنی فعال بودن خزش همه وب‌سایت‌های مناطق نیست. تا زمانی که اجرای واقعی خزش و ثبت خبر در داشبورد تأیید نشده، نباید سامانه را در وضعیت عملیاتی کامل تلقی کرد.

## قابلیت‌ها

- داشبورد React/Vite با API مبتنی بر Express و Node.js
- ذخیره‌سازی داده‌ها در PostgreSQL و schema مجزای `niopdc_app`
- ۳۷ رکورد مرجع مناطق عملیاتی
- ۱۸ منبع رسانه‌ای تعریف‌شده؛ ترکیبی از RSS و خزش HTML
- حذف خبرهای تکراری بر اساس نشانی canonical و hash
- ثبت سوابق اجرای جمع‌آوری، وضعیت منبع و خطاها
- تحلیل خبر، امتیازدهی، خوشه‌بندی رویداد و علامت‌گذاری موارد نیازمند بررسی
- احراز هویت API با نشست Supabase؛ مسیر سلامت سامانه عمومی است
- زمان‌بند داخلی با مقدار پیش‌فرض ۳۰ دقیقه؛ برای اجرای پایدار به میزبانی همیشه‌فعال یا زمان‌بند خارجی نیاز است

## وضعیت گردآوری منابع

وجود یک منبع در فهرست به معنی موفق بودن واکشی آن نیست. وضعیت واقعی هر منبع باید از خروجی `/api/sources` و سوابق `/api/collector/status` و `/api/logs` بررسی شود. آدرس RSS فقط برای منابعی تنظیم شده که مسیر آن‌ها در کد تأیید شده است؛ سایر منابع از خزش HTML استفاده می‌کنند و ممکن است به تنظیم اختصاصی نیاز داشته باشند.

منابع منطقه‌ای تا زمان گردآوری و تأیید نشانی رسمی هر منطقه به‌صورت فعال در فهرست ۳۷گانه معرفی نمی‌شوند. افزودن هر نشانی باید پس از بررسی مالکیت دامنه، دسترسی و ساختار خبر انجام شود.

## راه‌اندازی محلی

پیش‌نیازها: Node.js 22 یا بالاتر و npm.

```bash
npm ci
```

برای اجرای محلی با SQLite (صرفاً توسعه و آزمون)، فایل محیطی محلی را با مقادیر توسعه تنظیم کنید و سپس:

```bash
npm run db:setup
npm run db:seed
npm run dev
```

برای اجرای Production از PostgreSQL استفاده کنید؛ SQLite برای محیط عملیاتی پیکربندی توصیه‌شده نیست.

## متغیرهای محیطی Production

این مقادیر باید در بخش Environment میزبان تنظیم شوند؛ هیچ کلید یا رمز عبوری را در مخزن Git قرار ندهید.

| متغیر | کاربرد |
| --- | --- |
| `NODE_ENV` | مقدار `production` |
| `DATABASE_URL` | اتصال PostgreSQL به schema `niopdc_app` |
| `SUPABASE_URL` | نشانی پروژه Supabase |
| `SUPABASE_ANON_KEY` | کلید عمومی/publishable برای اعتبارسنجی نشست |
| `VITE_SUPABASE_URL` | نشانی Supabase برای فرانت‌اند |
| `VITE_SUPABASE_ANON_KEY` | کلید عمومی/publishable برای فرانت‌اند |
| `CORS_ORIGIN` | مبدأهای مجاز، جداشده با کاما؛ در Production فقط دامنه داشبورد |
| `NEWS_POLL_INTERVAL_MINUTES` | فاصله اجرای زمان‌بند؛ پیش‌فرض ۳۰ دقیقه |
| `GEMINI_API_KEY` | اختیاری؛ برای قابلیت‌های تولید و تحلیل مبتنی بر Gemini |

نمونه قالب اتصال دیتابیس (مقادیر واقعی را فقط در میزبان وارد کنید):

```text
postgresql://USER:PASSWORD@HOST:PORT/postgres?schema=niopdc_app&sslmode=require
```

در محیط عملیاتی، `PRISMA_DB_PUSH` را فعال نکنید؛ schema باید از قبل provision شده باشد. برنامه در زمان شروع اتصال دیتابیس را بررسی می‌کند و در صورت شکست، به‌جای نمایش وضعیت زنده غیرواقعی متوقف می‌شود.

## ساخت و اجرای Production

```bash
npm ci
npm run build
npm start
```

ساخت Docker:

```bash
docker build -t niopdc-monitor .
docker run --env-file .env -p 3000:3000 niopdc-monitor
```

برنامه باید روی `0.0.0.0` و پورتی که در متغیر `PORT` تعیین شده گوش دهد. برای Render از Dockerfile ریشه مخزن استفاده می‌شود.

## مسیرهای API

تمام مسیرهای زیر به‌جز `GET /api/health` به نشست معتبر Supabase نیاز دارند. عملیات مدیریتی مانند همگام‌سازی دستی، افزودن/ویرایش منبع و تغییرات حساس به نقش `admin` در `app_metadata` نیاز دارند.

| متد | مسیر | توضیح |
| --- | --- | --- |
| GET | `/api/health` | سلامت سرویس و اتصال دیتابیس |
| GET | `/api/auth/me` | کاربر و نقش نشست فعلی |
| GET | `/api/stats` | آمار زنده داشبورد |
| GET | `/api/articles` | جست‌وجو و فهرست اخبار |
| GET | `/api/sources` | منابع و وضعیت آن‌ها |
| POST | `/api/sources/:id/sync` | جمع‌آوری یک منبع؛ مدیر |
| POST | `/api/collector/sync` | جمع‌آوری دستی همه منابع فعال؛ مدیر |
| GET | `/api/collector/status` | وضعیت زمان‌بند داخلی |
| GET | `/api/regions` | فهرست مناطق |
| GET | `/api/events` | رویدادهای خوشه‌بندی‌شده |
| GET | `/api/rumors` | موارد نیازمند بررسی |
| GET | `/api/factchecks` | سوابق راستی‌آزمایی |
| GET | `/api/logs` | گزارش رخدادهای سامانه |
| POST | `/api/ai/rewrite` | بازنویسی خبر؛ نیازمند `GEMINI_API_KEY` |
| POST | `/api/ai/generate-package` | تولید بسته محتوایی؛ نیازمند `GEMINI_API_KEY` |

## زمان‌بندی و میزبانی

زمان‌بند داخلی هر ۳۰ دقیقه اجرا می‌شود و هنگام شروع سرویس نیز یک جمع‌آوری اولیه را با تأخیر کوتاه آغاز می‌کند. این زمان‌بند فقط تا زمانی کار می‌کند که فرایند سرور فعال باشد. سرویس‌های رایگان دارای خاموشی خودکار در زمان بی‌کاری برای پایش پیوسته مناسب نیستند؛ برای جمع‌آوری قابل اتکا باید از سرویس همیشه‌فعال یا زمان‌بند خارجی (برای مثال n8n) استفاده شود و نتیجه اجرای آن در `CollectionRun` ثبت گردد.

## راستی‌آزمایی پس از استقرار

1. `GET /api/health` باید پاسخ `2xx` و `database: connected` بدهد.
2. پس از ورود، `GET /api/sources` باید ۱۸ منبع مرجع را نشان دهد.
3. `GET /api/regions` باید ۳۷ منطقه را نشان دهد.
4. اجرای جمع‌آوری باید در `CollectionRun` ثبت شود و برای هر منبع وضعیت موفق/ناموفق و تعداد دریافت‌شده قابل مشاهده باشد.
5. فقط پس از مشاهده خبرهای واقعی و بررسی لینک و زمان انتشار آن‌ها، می‌توان گردآوری را تأییدشده دانست.

## امنیت

- کلیدهای Supabase، رمز دیتابیس و کلید Gemini فقط در متغیرهای محیطی میزبان نگهداری شوند.
- از قرار دادن رمز نمونه یا واقعی در README، فایل‌های نمونه قابل انتشار یا Commit خودداری شود.
- مبدأ CORS را به دامنه‌های موردنیاز محدود کنید.
- نقش مدیر باید از طریق `app_metadata.role=admin` در سمت مورد اعتماد تنظیم شود؛ `user_metadata` قابل ویرایش توسط کاربر نباید مبنای مجوز مدیریتی باشد.
